## 1. 结论摘要

1. **产品定位是陪伴，不是镜像。** 用户的表情不直接贴到形象上；感知结果与对话输出汇入**情绪状态机**，由它决定形象"如何、何时"回应——"你笑了，它稍后用它自己的方式回应你"。
2. **架构分四块**：感知层（ARKit/Vision）→ 情绪状态机 → 形象渲染；对话引擎（云端）作为状态机的另一路输入。**感知层永远不经过 LLM。**
3. **语音对话的使用方式**：手机立在支架上外放、每次短聊几分钟；**免唤醒，一直听**；要**听得出用户的语气**；回答用**同一个预置音色，并随情绪变化语气**。
4. **对话架构选方案 B**：实时语音模型直接听原始音频（因此能理解语气），**只输出带标签的文字**；标签同时驱动形象表情、动作和情感 TTS 的语气。**方案 C**（实时语音模型直接输出语音）为备选。纯级联（ASR → 文字 → LLM）听不出语气，不作为主方案。
5. **云端选型原则：一家厂商同时提供"可只出文字的实时语音模型"与"同音色、支持情感参数的 TTS"**；在满足条件的厂商中按 M2 的延迟实测定夺，不按价格。
6. **第一版不自建端侧 LLM。** 端侧小脑推迟到 M4，且是否启动由量化指标决定；届时首选 Apple Foundation Models，MLX 为备选。
7. **一直听靠两道闸门控制**：本地人声检测（不说话就不上传）+ 视线软闸门（不看屏幕就提高阈值或暂停）。
8. 现实门槛排序：**真机签名** > **外放下的回声消除与打断**（免唤醒能否成立取决于它）> **方案 B 的厂商能力验证** > **形象素材管线（VRM→USDZ）**。

## 2. 前提与约束

### 2.1 项目前提

- 个人自用，不上架、不对外提供服务，因此不需要生成式 AI 备案，也不需要后端代理服务器（上架前为必须项，见第 10 章备注）。
- API Key 存 iOS Keychain，不上传、不硬编码进仓库。
- 暂不考虑多用户、配额、计费、后台常驻。
- 典型使用：支架外放、单次几分钟。发热、耗电、成本不做专门设计。

### 2.2 硬约束

| 约束 | 具体限制 | 对设计的影响 |
|---|---|---|
| 内存 | 8GB 机型单 App 实际可用约 3–4GB，超出会被 jetsam 杀进程 | 自建端侧 3B 4bit（约 2GB 权重 + KV cache）逼近警戒线 |
| entitlement | 自建 3B 模型大概率需要 `increased-memory-limit`；免费个人团队是否支持需确认 | 优先 Foundation Models 的理由之一 |
| 热 | 持续推理 2–3 分钟后降频 | 不设计长时间连续推理；视觉任务限流 |
| 后台 | 锁屏/切后台后摄像头、麦克风与推理均停止 | 不做"后台陪伴"；切后台即断开实时会话 |
| 签名 | 免费 Apple ID 仅 7 天有效期，需连 Mac 重签；部分能力（如 Push）不可用 | 已决定先用免费方案，每周固定重签 |
| 网络 | 云端调用依赖公网；实时语音为长连接 WebSocket | 必须有断网/弱网降级与重连路径 |
| 摄像头 | ARKit 运行时独占摄像头 | 所有视觉任务都跑在 `ARFrame` 上，不另开 `AVCaptureSession` |
| 外放回声 | 支架外放，扬声器声音会被麦克风拾取 | 回声消除是免唤醒的前提（4.7） |

## 3. 总体架构

```
 摄像头 ─▶ 感知层 (ARKit 人脸/视线 + Vision 手势) ─▶ 感知特征 ─────────┬──────────────┐
                                                      (视线软闸门) │              ▼
                                                                   ▼    ┌──────────────────┐
 麦克风 ─▶ 回声消除 ─▶ 本地人声闸门 ─▶ 实时语音模型（只出文字）─▶ 标签解析 ─▶│    情绪状态机     │─▶ 形象渲染
                                       │ 听原始音频，理解语气            │    │ (本地、规则、无模型) │
                                       └─ 回答文字 + 标签 ───────────────┤    └──────────────────┘
                                                                         ▼
                                                     分句 ─▶ 情感 TTS（同一音色）─▶ 扬声器
                                                                         （同一音频引擎，供回声消除参考）
```

| 模块 | 职责 | 时间预算 | 依赖 |
|---|---|---|---|
| 感知层 | 人脸表情系数、视线/距离、手势 → 感知特征；提供视线软闸门信号 | 30–50 ms | 无网络、无模型下载 |
| 情绪状态机 | 汇总感知特征、用户语气、助手情绪与动作，决定形象的表情、动作、视线与回应时机 | < 16 ms（每帧） | 本地规则 |
| 对话引擎 | 收音闸门、听懂（含语气）、回答、说（含语气） | 见第 6 章 | 网络 + 云 API |
| 形象渲染 | 把状态机输出的"形象自己的"表情权重、动作、口型播放出来 | 60 fps | 本地 |

## 4. 分模块选型

### 4.1 感知层（视觉）

| 能力 | 方案 | 频率 | 说明 |
|---|---|---|---|
| 人脸表情 | **ARKit `ARFaceAnchor.blendShapes`** | 60 fps | 52 维表情系数，作为**情绪状态机的输入**，不直接映射到形象 |
| 视线 / 注视 | `ARFaceAnchor.lookAtPoint`、人脸是否在画面中 | 60 fps | 两个用途：形象视线跟随用户（"它在看我"）；为收音提供**视线软闸门**（4.4） |
| 距离（靠近/后退） | `ARFaceAnchor.transform` 的 z 分量 | 60 fps | 随人脸追踪免费获得 |
| 手势 | Vision `VNDetectHumanHandPoseRequest`，跑在 `ARFrame.capturedImage` 上 | 10–15 fps | 21 个关节点；挥手/比心/点赞等语义自行判断。iOS 上 ARKit 无手部关节 API |
| 场景/物品 | 不在端侧做 | — | 后续走云端多模态（见 4.12） |

- **为什么是 ARKit 而不是 Vision**：Vision 的 `VNFaceObservation` 只有关键点、roll/yaw/pitch 与 captureQuality，没有表情语义；ARKit 直接给出 52 维系数。
- **负载**：ARKit 人脸追踪由系统完成；真正跑 Vision 推理的只有手部一路，10–15 次/秒。
- **session 封装**：ARKit 配置集中在一个可替换的 `PerceptionSource` 实现里。未来"看物品"可能改用 `ARWorldTrackingConfiguration` + `userFaceTrackingEnabled`（前后摄同时开），但**M1 不实现**，只保证可替换。

### 4.2 情绪状态机

整个产品体验的核心，纯本地规则，不用模型。

**输入**

- 感知特征：平滑后的表情强度（笑、皱眉、惊讶等由 blendShape 组合规则得出）、是否在看、距离变化、手势事件。
- 对话事件：用户开始/结束说话、**用户语气**（`<user:…>` 标签，见 4.5）、助手情绪与动作（`<emo:…>` / `<act:…>` 标签）、助手开始/结束说话、TTS 音频电平（口型）。
- 时间：空闲时长、上次反应时间。

**状态（初版）**

| 状态 | 进入条件 | 形象表现 |
|---|---|---|
| Idle | 无人脸 / 长时间无交互 | 呼吸、眨眼、四处看 |
| Attending | 检测到用户看向屏幕 | 视线跟随、轻微点头 |
| Listening | 本地人声闸门打开 | 专注表情、偶尔点头 |
| Thinking | 用户说完、等待回答 | 思考表情/动作（0 ms 进入）；收到 `<user:…>` 时先切换到对应神情（如用户低落 → 关切） |
| Speaking(emotion) | 助手开始说话 | 按 `<emo:…>` 切换表情，口型由音频驱动 |
| Reacting | 感知到用户表情/手势事件，或收到 `<act:…>` | 播放对应回应/动作，结束后回到前一状态 |

**行为原则**

1. **回应而非复制**：用户笑 → 形象 300–800 ms 后用它自己的表情集回应，幅度与样式不同于用户。
2. **语气优先于表情**：用户脸上平静、语气低落时，以语气为准；两者一致时增强反应幅度。
3. **去抖**：blendShape 做时间平滑 + 阈值滞回，避免表情抖动。
4. **冷却**：同一类反应设冷却时间，避免连续重复。
5. **优先级**：Speaking 中的情绪标签 > 动作标签 > 感知反应 > Idle 微动作；眨眼、呼吸始终叠加。
6. **视线是唯一允许"跟随"的通道**：形象看向用户脸部位置。

**口型**：第一版用 TTS 输出音频的电平驱动 `jawOpen` 等口部形变；若所选 TTS 返回音素/字级时间戳，再升级为按音素对口型。

**输出**：`AvatarPose`——形象**自己的** blendShape 权重 + 头部/视线朝向 + 动作片段 ID。

### 4.3 对话引擎：方案 B 为主，C 为备选

| 方案 | 组成 | 能听语气 | 回答声音 | 能出情绪标签 | 定位 |
|---|---|---|---|---|---|
| **B** | 实时语音模型（输入音频，**只输出文字**）→ 标签解析 → 分句 → 情感 TTS | 是（模型直接听原始音频） | 情感 TTS，同一音色，可控 | 是 | **主方案** |
| **C** | 实时语音模型（输入音频，直接输出语音 + 文字转写） | 是 | 模型自带音色，语气最自然但不可控 | 难：文字里的标签会被念出来 | **备选**：B 的厂商条件不满足时启用 |
| A | 流式 ASR（带情绪识别）→ LLM → 情感 TTS | 依赖 ASR 的情绪识别，较粗 | 情感 TTS | 是 | 仅在 B、C 都不可用时考虑 |

**选 B 的理由**：同时满足"听得出语气"（模型直接听音频）、"同一音色 + 情绪变化"（情感 TTS）、"标签驱动表情"（输出是文字）、"免唤醒"（实时接口一般自带服务端端点检测与打断）。代价是比 C 多一跳 TTS，约 0.2–0.5 s。

**B 的关键前提（M2 第一周验证，见 V4–V6）**

1. 厂商的实时语音接口可设置为**只输出文字**（输出模态仅 text）。
2. 只输出文字时，模型**仍会理解并利用用户的语气**——在回答内容和 `<user:…>` 标签中体现出来，而不是只基于转写文字作答。
3. 同一厂商提供**支持情感参数、且有同一音色**的流式 TTS。

据目前了解：OpenAI Realtime、Qwen-Omni（阿里百炼）的实时接口支持只输出文字；豆包实时语音是否支持需确认。TTS 侧，阿里 CosyVoice、豆包"多情感"音色支持情感控制（需确认具体参数）。

**方案 C 的补偿措施**（若启用）

- 形象情绪：用本地分类器（`NLEmbedding` / Foundation Models）从回答转写文字中推断，或从模型输出音频的电平/语速粗略推断。
- 音色一致：预合成短句改用该模型自身的音色录制缓存（若厂商提供同音色 TTS），否则取消预合成短句，只保留非语言反馈。

**厂商选型原则**

1. 必须同时满足上面三个前提（选 C 时只需实时语音模型）。
2. 在满足条件的厂商中，以 M2 的 M_answer 实测定夺（常态/高峰）；成本不构成决策因素（第 8 章）。
3. 优先国内厂商（阿里百炼、火山引擎豆包）；OpenAI 依赖海外网络，作为备选。
4. 接入方式：`URLSessionWebSocketTask` + 厂商实时协议；TTS 走厂商 WebSocket/HTTP 流式接口；不引入重型 SDK。

### 4.4 收音：一直听的两道闸门

免唤醒一直听，但不能把所有声音都送上云端。

| 闸门 | 方案 | 作用 |
|---|---|---|
| **本地人声闸门（硬）** | 首选 iOS 26 `SpeechAnalyzer` 的 `SpeechDetector` 模块（需确认可独立使用及效果）；兜底为能量阈值 + 过零率 | 只有检测到人声才开始向实时会话推送音频；静音、环境噪音不上传，控制计费与隐私 |
| **视线软闸门** | 感知层"是否在看屏幕" | 用户在看：正常阈值；离开视线超过数秒：提高人声阈值；无人脸超过 30 s：暂停收音并断开实时会话，人脸重新出现时自动恢复 |
| 服务端端点检测 | 实时语音接口自带的 server VAD | 判定一句话说完、触发模型作答；静音超时初值 500 ms，按误切率调整 |

- 闸门打开前保留 300–500 ms 的音频预缓冲一起送出，避免句首被截掉。
- **收音状态始终可见**：形象的倾听姿态即是提示；另提供一个静音手势或按钮，静音时形象做出"捂耳朵"等明确姿态。
- **电视、旁人说话**：视线软闸门是主要手段；仍误触发时，M3 可评估说话人确认（个人声纹），首版不做。

**独立 ASR 的位置**：方案 B/C 下不需要单独的 ASR。端侧 `SpeechTranscriber`（需确认支持 zh-CN）只用于两处：断网时的本地指令识别（4.8），以及可选的本地快速指令通道。WhisperKit 不采用（非原生流式、静音段易编造内容、中文简繁混出、增加 100–200 MB）。

### 4.5 模型输出契约（标签）

实时语音模型只输出文字，文字中携带三类句首/行内标签，全部是固定枚举（完整枚举以 `specs/002-m1-presence/data-model.md` 为准，语法与解析规则见 `specs/003-m2-voice-conversation/contracts/tag-protocol.md`）：

| 标签 | 含义 | 示例枚举 | 消费方 |
|---|---|---|---|
| `<user:…>` | 模型从语气中听出的用户情绪，每轮回答开头输出一次 | `happy` / `calm` / `sad` / `tired` / `angry` / `anxious` | 情绪状态机（Thinking 阶段先切换神情）、会话记忆 |
| `<emo:…>` | 形象说这句话时的情绪 | `happy` / `gentle` / `sad` / `surprised` / `shy` / `playful` | 情绪状态机（表情）、TTS（情感参数） |
| `<act:…>` | 形象执行的动作 | `nod` / `spin` / `wave` / `heart` 等，与动作片段库一一对应 | 情绪状态机（动作） |

- 示例：`<user:tired><emo:gentle>今天累坏了吧？<act:nod>先歇会儿，我陪着你。`
- **不用 JSON**：流式输出下 JSON 无法边收边播。
- **解析**：流式接收 → 标签解析器剥离标签并发出事件 → 剩余文本进入分句器（按 `。！？…` 切分，并设长度上限）→ TTS。
- **对齐**：`<emo:…>` 作用于其后的句子，在该句音频开始播放时生效，同时作为该句 TTS 的情感参数；`<act:…>` 在其所在位置对应的音频播放时触发。
- **容错**：缺失或非法标签时沿用上一个值；system prompt 中给出枚举与示例。
- **`<emo>` → TTS 情感参数映射表**：按所选厂商的情感枚举建立一张映射表，厂商不支持的情绪就近映射（如 `shy` → 温柔）。

### 4.6 语音合成（TTS）

| 要求 | 说明 |
|---|---|
| **同一音色 + 情感参数** | 厂商选型硬条件（4.3）。每句按 `<emo:…>` 设置情感参数 |
| 流式 | 分句流式合成，首包越快越好 |
| 预合成短句 | 附和、问候、垫场语等用**同一音色、多种情感**预合成，缓存在本地，播放 0 延迟 |
| 时间戳（加分项） | 返回音素/字级时间戳可用于精确口型（4.2） |
| 断网兜底 | `AVSpeechSynthesizer`，仅断网时使用 |

### 4.7 音频会话：回声消除与打断

支架外放时扬声器的声音会被麦克风拾取。回声消除做不好，本地人声闸门会被形象自己的声音打开，造成"自问自答"——**免唤醒能否成立取决于这一节**。

- **会话配置**：`AVAudioSession` 使用 `.playAndRecord` + `.voiceChat`，选项含 `.defaultToSpeaker`（否则默认走听筒）与蓝牙；`AVAudioEngine.inputNode.setVoiceProcessingEnabled(true)` 开启系统级回声消除。
- **播放走同一个 `AVAudioEngine`**（`AVAudioPlayerNode`），让回声消除拿到参考信号。
- **打断（barge-in）**：播放期间持续检测人声；确认插话后立即停播、丢弃剩余音频与未完成的文字流，并通知实时会话取消当前回答，转入新一轮收听。实时接口自带的打断事件与本地检测取先到者。
- **防误打断**：开了回声消除仍有残留回声。播放期间提高本地人声阈值，并要求连续检测到人声 200–300 ms 才判定为插话。
- **音频格式**：按厂商要求重采样（通常 16 kHz / 24 kHz、16-bit PCM 单声道）后推送。
- 注意：语音处理开启后系统会压低其他音频音量（ducking），属预期行为。

### 4.8 指令、离线与垫场

方案 B 下，闭集指令（"笑一个""转个圈""打招呼"）由模型直接输出 `<act:…>` 标签完成，不需要本地意图路由。本地只保留两条通道：

| 通道 | 何时启用 | 方案 |
|---|---|---|
| 离线模式 | 断网 / 实时会话不可用 | 端侧 `SpeechTranscriber` 转写 → 关键词 / `NLEmbedding` 意图匹配 → 动作 + 预置话术（随机变体 + 情绪槽位）+ `AVSpeechSynthesizer` |
| 本地快速指令（M3 可选） | 在线时，闭集指令经云端约 1 s 才响应、体感偏慢时 | 端侧 `SpeechTranscriber` 与实时会话并行运行，命中闭集指令时立即执行动作；云端回答到达后去重 |

覆盖率等数字全部待测，不预设。

**垫场短句**：只在预计较慢时触发（如 TTFT 超过阈值仍无输出），取自预合成缓存，0 ms 播放；**不是每轮都播**。Thinking 状态的非语言反馈则每轮都有。

### 4.9 会话与记忆

实时语音接口在一次 WebSocket 连接内由服务端保存对话状态。因此：

- **会话内**：上下文由服务端会话持有；客户端同步记录每轮的用户转写（取实时接口的输入转写事件，需确认可用）、模型回答与 `<user:…>` 标签。
- **会话外（客户端是唯一事实来源）**：每次建立实时会话时，由客户端注入人格设定 + 长期事实 + 最近摘要；会话结束或断线重连时，由客户端重建上下文。云端不长期保存会话。
- **注入上限（初值）**：人格 ≤ 800、长期事实 ≤ 500、摘要 ≤ 500 token；短聊场景下会话内历史不额外截断，超过约 20 轮时由客户端发起摘要并重建会话。
- **更新**：会话结束后异步调用一次文本模型生成摘要、抽取长期事实（含用户近期的情绪趋势）；不阻塞对话。
- **存储**：本地 SwiftData。

### 4.10 端侧小脑（M4，条件启动）

**启动条件**：第 6 章 M_answer 在完成所有低成本优化后 p50 仍 > 1.5 s，或离线体验成为实际痛点。

**端侧模型只解决延迟与离线，不解决能力，也听不出语气。** 它只能接管闭集与浅层闲聊；若目标是"聊得更深"，投入应放在云端。

| 项 | 首选 | 备选 |
|---|---|---|
| 运行时 | **Apple Foundation Models**（系统自带约 3B 模型）：零下载；跑在系统进程，不占 App 内存额度（需确认）；流式、`@Generable` 结构化输出、tool calling、`prewarm()` | MLX Swift（再备选 llama.cpp/Metal）：需自行处理分词、KV cache、采样；3B 逼近内存警戒线 |
| 模型 | 不可选 | Qwen3-1.7B / 4B（**必须关闭思考模式**）、Gemma 3n E2B/E4B；M4 时再看当时最新版本 |
| 限制 | 上下文约 4k、拿不到 logprob、不能换模型 | 需确认免费签名能否使用 `increased-memory-limit` |
| 量化 | — | 4bit（1B ≈ 0.7 GB，3B ≈ 2 GB 权重） |

**硬门槛**：Foundation Models 依赖 Apple Intelligence，需确认设备在当前地区与 Apple ID 设置下能否开启、中文是否支持（M0 一行代码验证）。

### 4.11 形象渲染

| 方案 | 定位 | 说明 |
|---|---|---|
| **RealityKit + USDZ（52 blendShape）** | 首选 | 用 `BlendShapeWeightsComponent` 驱动（iOS 18+，需确认）；表现力强 |
| Live2D（Cubism SDK for Native） | 备选 | 若走二次元 2D 路线；需第三方引擎集成 |
| 序列帧 | 仅占位 | 只能播离散状态，**无法被连续系数驱动**；可在素材未就绪时用于调试状态机 |
| SceneKit | 不采用 | 已进入弃用流程（需确认） |

**素材管线是 M1 的第一个技术风险**：

- 候选素材：VRoid 模型中带 Perfect Sync（52 个 ARKit blendShape）的。
- VRoid 输出 VRM（基于 glTF），**RealityKit 不能直接加载**，需经 Blender 等转为 USDZ，blendShape、骨骼、材质是否完整保留需实测。
- 动作片段（点头、转圈、挥手等）需随模型一并准备，与 `<act:…>` 枚举一一对应。
- 备选：在 Blender 中自建简化风格化模型并绑定 52 个形变。
- 注意模型的使用许可。

### 4.12 云端多模态"看图"（不进 MVP）

- 触发：用户主动说"看看这个"时拍单帧、压缩上传，不做持续视频流。
- 隐私：个人自用不构成问题。
- 摄像头：看物品通常需后置摄像头；4.1 的 session 封装已为此预留。

## 6. 延迟指标与预算

### 6.1 指标定义（起点均为用户实际停止发声的时刻）

| 指标 | 含义 | 目标 |
|---|---|---|
| **M_feedback** | 形象出现倾听/思考反应 | < 100 ms，每轮都有 |
| **M_answer** | **实质回答**的第一个音节（不含垫场短句） | M2 测基准；p50 < 1.5 s 是 M4 是否启动的门槛 |
| M_reflex | 用户表情/手势 → 形象开始回应 | 300–800 ms（刻意延迟，见 4.2） |
| M_track | 视线跟随延迟 | < 100 ms |
| M_bargein | 用户插话 → 形象停止发声 | < 300 ms |

垫场短句不计入 M_answer，否则该指标形同虚设。

### 6.2 预算（估算，需实测）

| 环节 | 方案 B | 方案 C | 备注 |
|---|---|---|---|
| 服务端端点判定 | 300–600 ms | 300–600 ms | 静音超时，固定成本 |
| 模型首个输出 | 300–800 ms | 300–800 ms | 随会话内上下文增长；受厂商高峰波动影响 |
| 攒够第一句 | 150–400 ms | — | 取决于输出速度与分句长度上限 |
| TTS 首包 | 200–500 ms | — | 流式情感 TTS |
| **M_answer 合计** | **≈ 1.0–2.3 s** | **≈ 0.6–1.4 s** | 端点判定后各环节基本串行 |

方案 B 比 C 慢约 0.4–0.9 s，换来的是可控音色、情绪标签与预合成短句的一致性。若 B 的实测 p50 明显超过 1.5 s，可缩短分句长度上限（首句只攒几个字即送 TTS）。

## 7. 实施顺序

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M0** | 免费账号签名、真机跑通空工程；一次性能力探测 | ① 安装到设备，并走通一次 7 天到期后的重签；② 打印并记录：`SystemLanguageModel.default.availability`、`SpeechTranscriber.supportedLocales` 是否含 zh-CN、`SpeechDetector` 是否可用、`NLEmbedding.sentenceEmbedding(for: .simplifiedChinese)` 是否非 nil |

| **M2b** | 对话引擎全链路：两道收音闸门、回声消除、打断、标签解析、分句、情感 TTS、口型 | ① 支架外放连续 10 轮，无一轮把自己的声音当输入，无误打断；② 播放中插话可打断，M_bargein < 300 ms；③ 电视背景声下 5 分钟不看屏幕，不产生误触发对话；④ 产出 M_feedback / M_answer 的 p50/p90 基准与候选厂商对比，据此定厂商 |
| **M3** | 会话记忆 + 离线模式 + 预置短句 +（可选）本地快速指令 | ① 会话注入不超过 4.9 的上限，断线重连后人格与上下文延续；② 断网有兜底（本地指令 + 预置话术 + 系统 TTS）；③ 人格与音色跨轮一致 |
| **M4** | 端侧小脑（条件启动，见 4.10） | 本地命中率 > 60%，命中时 M_answer < 1.0 s |

M1 与 M2 可以并行；M1 不应跳过，它是产品体验的地基。

## 8. 成本估算（个人用量）

实时语音模型按音频输入时长/音频 token 计费，单价高于纯文本，但两道收音闸门保证只有说话的部分才上传。

按一天 20 轮、每轮用户说话约 10 s、模型输出 100 字估算，月音频输入约 100 分钟，另加每次会话注入的上下文与 TTS 合成约 6 万字：

| 项 | 月成本量级 |
|---|---|
| 国内实时语音模型（只出文字） | 几元至几十元 |
| 国内情感 TTS | 几元至十几元 |
| OpenAI Realtime | 几十至一百余元 |

**结论：成本不构成决策因素，因此也不是厂商选型标准。** 唯一要防的是"一直听"把环境声持续上传，由 4.4 的闸门解决。

## 9. 决议与待验证项

### 9.1 已决议

| 议题 | 结论 |
|---|---|
| 表情识别用 Vision 还是 ARKit | ARKit。Vision 无表情语义字段 |
| 表情 + 手势 + 姿态能否同时 60 fps | 不需要：人脸 60 fps（ARKit），手势 10–15 fps，人体姿态移除，距离用人脸 z 分量 |
| 语音对话架构 | 方案 B（实时语音模型只出文字 + 情感 TTS），方案 C 备选；纯级联听不出语气，不作为主方案 |
| 开始说话的方式 | 免唤醒一直听，由本地人声闸门 + 视线软闸门控制 |
| 语气理解 | 由实时语音模型直接听音频完成，通过 `<user:…>` 回传；不单独做语音情绪识别 |
| 回答的声音 | 同一预置音色 + 按 `<emo:…>` 变化语气；预合成短句同音色 |
| 使用场景 | 支架外放、短聊；回声消除为 M2 第一优先级 |
| ASR 是否引入 Whisper | 不引入；方案 B/C 下不需要独立 ASR，端侧系统识别只用于离线与快速指令 |
| 第一版是否做端侧 LLM | 不做。由 M_answer 指标决定 M4 是否启动 |
| MediaPipe LLM Inference | 移出选型（已向 LiteRT-LM 迁移，且 Foundation Models + MLX 已覆盖） |
| 端侧模型型号 | 推迟至 M4；候选 Foundation Models、Qwen3、Gemma 3n |
| 云端看图 | 不进 MVP；session 封装预留前后摄 |
| 形象定位 | 陪伴而非镜像；引入情绪状态机 |
| 闭集指令 | 方案 B 下由模型输出 `<act:…>`；本地意图匹配只用于离线与可选快速通道 |

## 10. 明确不做的事

| 项 | 原因 |
|---|---|
| 把用户表情直接映射到形象（镜像） | 与陪伴定位冲突；视线跟随除外 |
| 唤醒词 / 按住说话 | 已选免唤醒；iOS 无系统唤醒词 API，自研成本高 |
| 纯级联作为主方案 | 听不出语气 |
| 独立的语音情绪识别模型 | 由实时语音模型直接听音频完成 |
| 声音克隆 | 已选预置音色 |
| 说话人确认（声纹） | 首版靠视线软闸门；M3 视误触发情况再评估 |
| 端侧多模态 VLM | 参数量与内存不允许 |
| 人体姿态检测 | 前置摄像头基本只拍到上半身；距离用人脸 z 分量 |
| 端侧情绪分类模型 | 表情用 blendShape 组合规则，语气由云端模型给出 |
| MediaPipe LLM Inference、WhisperKit | 见 9.1 |
| 实时云端视频流理解 | 流量与延迟成本过高 |
| 后台/锁屏常驻 | 系统限制 |
| 主动推送提醒 | 免费签名不支持 Push Notifications |
| 自建后端代理 | 个人自用无必要；**正式上架前为必须项**，见下方备注 |

> **备注：自建后端代理**
>
> 当前跳过是因为本 App 只有自己一台设备在用，Key 泄露不构成实际风险。但**一旦决定正式上架 App Store（或分发给任何第三方），这件事是 must，不能延期，也不能用"先这样发出去再说"的方式绕过**，理由有三条，且都是不可协商的：
>
> 1. **API Key 必然泄露**：客户端包的字符串可被反编译提取，Key 一旦公开，任何人可用你的额度，成本不可控。
> 2. **平台审核要求**：含生成式 AI 能力的应用需要可追溯的调用链路与内容安全措施，直连第三方 API 通常无法满足审核与备案要求。
> 3. **无法止损**：直连架构下，出问题时只能靠发新版，而审核周期通常以天计；有服务端才能即时关闭入口、限流、封禁。
>
> 迁移成本不高（客户端只需把 base URL 指向自己的域名；实时语音的 WebSocket 需由服务端中转或签发临时令牌），但**必须在架构上预留**：云端调用全部收敛在第 5 章的 Session / Provider 实现内部，届时只需替换实现，不动业务层。
