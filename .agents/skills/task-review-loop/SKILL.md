# Task Implementation & Independent Review Loop

每个任务实施完成（或按外部评审意见返工完成）、向用户汇报验收前，执行本闭环（最多 5 轮）。本规范不绑定特定 CLI、模型或技术栈，支持与 `task-handoff` 上下游衔接，也支持在无执行单时独立运行，并具备跨 CLI 自动降级能力。

## 第 0 步：项目上下文发现（零配置可用，有约定优先继承）

执行闭环前，先只读核对目标仓库根目录的规范文件（若存在，如 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`），提取并继承：

- **项目红线**：禁读/禁改路径、只读基线保护、禁止审查员执行的写副作用命令；
- **验收门禁命令**：项目约定的测试、lint、类型检查、构建或只读校验命令（未约定时按仓库技术栈自动探测）；
- **收口策略**：默认在用户明确确认验收前不 `git commit`、不 `git push`、不勾选项目任务追踪项（若项目另有约定则从其约定）；
- **首选审查模型**：若项目指定了高思考审查模型名，优先采用。

## 适用边界与红线

- **严格遵守项目红线**：无论实施方还是复审方，必须完整遵守从项目规范继承的全部红线。
- **不得提前收口**：在向用户汇报并得到明确确认前，按默认收口策略**不得勾选项目任务追踪项（如 `tasks.md`）、不得 `git commit`、不得 `git push`**（除非项目规范或用户明确授权）。
- **审查员零副作用**：审查员只允许只读读取、只读查询与无副作用检查（如运行只读单测、lint、类型检查或无写盘探测命令），**严禁修改任何文件，严禁运行会向仓库、产物目录或外部环境写入状态的命令**。
- **意见分级**：
  - **阻断项**：功能/逻辑 bug、违背定稿执行单/需求/项目原则、执行单自身遗漏或假设有误导致的真实缺陷、跨模块漏接或只读保护破坏、测试假阳性或缺失关键反例、实测口径失真或不可追溯、隔离性/安全性被破坏。
  - **非阻断建议**：风格微调、可读性改进、改动面较大可延后到后续任务的优化。

## 闭环步骤（最多 5 轮）

### 第 1 步：完成实现与送审前自检

1. **按基线完成实现**：
   - 若存在已拍板定稿的执行单（默认 `docs/handoffs/<task>-handoff.md`），严格按其改动范围、不做清单、接口契约、测试矩阵与偏差止损规则完成代码、测试与附加文档更新；
   - 若未走 `task-handoff` 流程，则按用户任务要求与项目规范完成实现。
2. **跑通完整验收门禁**：运行对应单测、全量测试、lint/类型检查/构建，以及项目约定的只读基线校验。
3. **检查仓库干净度**：核查 `git status` / `git diff`，确认无意外改动、无遗留临时文件或空目录、历史只读产物未动，且收口动作尚未提前执行。
4. **留存送审前防篡改快照指纹（跨平台纯 Git 原生）**：在派发审查员前记录以下三项输出，用于在审查员返回后核验字节级零修改：
   ```bash
   git status --porcelain
   git diff | git hash-object --stdin
   git diff --cached | git hash-object --stdin
   ```
   （若存在未跟踪的新增文件，亦须确认其列表及内容在审查前后未发生变化。）

### 第 2 步：派发独立只读复审（Round 1）

启动一个**隔离上下文的独立审查员**（看不到主会话的实现过程和推理历史），按以下三级优先级选择机制（工具无关，自动降级）：

1. **首选 · 单节点高思考审查员（适用于支持按模型/思考等级拉起单节点的工具，如 Antigravity 的 `swarm`）**：
   - **仅拉起 1 个审查节点**（首轮如 `name="reviewer"`，外部评审返工轮如 `name="reviewer-v2"`，`workspace="inherit"` 不建 worktree，严禁并发拉起多个节点）；
   - 指定高思考/强推理模型：优先采用项目指定的审查模型；未指定时，**默认选同系列 `High` 档位（如 `*-high`）**（仅在 `High` 不可用时就近回退，**不默认自动升级到 `XHigh`**，除非用户或项目规范明确要求），实现“实施省额度、审查保质量”；
   - 若审查节点默认具备写工具，必须在 `brief` 中明文约束只读零修改与禁写副作用命令；**每轮复审返回后比对送审前快照指纹确认零修改**；
   - 闭环结束后立刻回收（`kill`）该审查节点。
2. **降级 1 · 独立只读子代理（适用于无单节点精确模型能力但支持子代理的 CLI，如只读 `research` 子代理 / Agent / Task 工具）**：
   - 派发隔离上下文的只读子代理；若接口支持模型档位或思考等级参数，优先选高档位（如 `pro` / `high`），否则继承主会话配置。
3. **降级 2 · 无子代理能力兜底**：
   - 若当前 CLI 完全不支持派发子代理，须在最终汇报中明确注明“当前工具无子代理能力，跳过独立子代理复审”，按下方必查清单完成逐项自查并附上完整证据与改动清单，直接交用户或外部模型复审。

**发给审查员的 `brief` 必须明文包含以下 4 项**（新节点看不到主会话上下文，不得省略）：
1. **本 skill 的实际文件路径**（由主会话填入当前加载到的 `task-review-loop/SKILL.md` 真实路径，切勿写死 `.agents/skills/...`），要求先完整阅读该文件（必要时参阅同目录 `references/checklists.md`），按零信任原则、双重审查视角与 6 类攻击面必查清单执行；
2. **只读红线与项目红线**：禁止修改任何文件、禁止运行向仓库/产物目录写文件的命令，并明文列出从项目规范继承的全部红线；
3. **审查目标与范围**：目标执行单路径（若有）或任务需求/规范说明、本轮改动说明（如属外部评审返工，一并附上外部评审意见原文）；
4. **统一输出格式**：**结论（通过 / 需修改）→ 阻断项（带 `file:line` 与复现/反证依据）→ 非阻断建议 → 逐项核查证据**。

#### 审查员核心审查纪律（零信任 + 双重审查 + 6 类必查攻击面）

- **零信任独立复验**：不得轻信实施方在 `brief` 中的口头汇总；必须自己运行只读 `git status` / `git diff` 确认**真实全量改动面**，直接读取改动源码与测试全文，并按需独立复跑关键只读测试/校验命令。
- **双重审查视角**：
  1. **对照基线查落地**：是否完整落实定稿执行单（或任务需求）的改动范围、不做清单、接口契约、测试矩阵与文档更新点；
  2. **跳出基线找真实工程缺陷**：不得盲信执行单中的所有假设；主动核查跨模块调用方、第三方库真实源码/运行时行为与端到端业务路径——**即使执行单本身写漏或假设有误，只要构成真实 bug 或风险，同样判为阻断项**。
- **6 类高频攻击面必查清单（逐项过筛，分栈细项见 [references/checklists.md](./references/checklists.md)）**：
  1. **跨模块接线与复用一致性**：新建的工厂/辅助函数/配置是否真正接入所有生产调用方？同类入口（CLI / API / UI / Worker / 脚本等）是否漏改或重复造轮子？
  2. **第三方依赖与并发/资源生命周期陷阱**：必要时只读核查依赖源码或实测行为（线程/协程安全、阻塞事件循环、连接/文件句柄/缓存/临时文件回收、多余权限或暴露面）；
  3. **异常路径与边界输入**：空输入、空值、非法/极端数值、坏文件、外部服务断连或链路中途抛错时，状态是否完整回滚清理？是否杜绝静默吞错或静默降级创建脏状态？
  4. **测试真实性与断言强度**：有无假阳性或弱断言（如仅断言非空/状态码成功、过度 mock 掩盖真实逻辑、漏断言透传参数或副作用、未固定时钟/随机种子导致非确定性）？正反例与既有兼容回归是否齐备？
  5. **实测数字与文档口径真实性**：测试数、耗时、统计数是否与最后一次实测输出逐字一致？验证方式（真实联调 vs 脚本/Mock 模拟）表述有无夸大？代码变更后受影响的验证/产物是否基于**最终代码**重跑？执行单与项目文档有无残留旧表述？
  6. **只读保护与仓库干净度**：项目历史只读产物/锁文件是否完好？有无残留临时文件/空目录/调试打印？任务追踪项与 Git 状态是否符合收口策略？

### 第 3 步：核实意见、严格修复或举证异议

收到复审报告后，**先比对送审前快照指纹确认审查员零修改**，再逐条核实：

- **认同的阻断项**：必须根因修复，并补齐针对该阻断项的确定性回归测试。
  - **实施方修复纪律**：严禁通过静默吞错、删测试、放宽断言来“消除”阻断项；若发现阻断项涉及修改既定接口签名、改写既有测试预期或扩大改动范围，须按执行单的“偏差止损规则”审慎评估或先上报用户。
- **认同的非阻断建议**：仅在**改动小、低回归风险**时顺带修复；涉及较大重构或范围膨胀的，记入后续待办而非强行塞进本轮。
- **有异议的条目**：不得直接忽略；必须整理具体 `file:line`、规范条款或实测命令输出，说明为何不改。
- **同步与全量回归**：每次修复后，必须同步清理执行单与相关文档中的关联旧表述，并重跑全量验收门禁（若改动影响了已做过的实机联调或产物，须基于最新代码重跑），**严禁拿未过全量门禁的半成品唤醒下一轮复审**。

若本轮**阻断项 = 0 且无待审核的修复或未决异议**，闭环顺利结束（先回收审查节点），跳至第 5 步。

### 第 4 步：提交下一轮复审（Round 2 … 5）

- 再次留存送审前快照指纹（`git status --porcelain` + `git diff` / `git diff --cached` 哈希）；
- **优先复用同一审查员会话**（单节点 `swarm` 在公告板 `@reviewer` 续聊；子代理向原会话继续发消息），节省重复上下文并保持审稿口径连贯；
- 若当前 CLI 不支持向同一审查会话继续对话，则新开只读审查会话并完整附上：上一轮问题清单、本轮 `git diff`（或改动摘要与文件行号）、最新全量验证输出、以及异议与证据；
- **Round 2+ 审查聚焦与防漂移**：要求审查员重点复核 ① 上轮阻断项是否真正根治且有回归测试；② 异议证据是否成立；③ 本轮修复是否引入新回归（含文档同步）；不得对未改动代码反复冒出新的低优先级风格意见卡通过（但发现遗漏的真实严重缺陷仍应阻断）；
- 回到第 3 步，重复循环。

### 终止条件

满足以下任一条件即停止循环（停止前务必回收审查节点并比对快照指纹确认审查员零修改）：

1. **一致通过**：审查方判定阻断项 = 0，且双方无未决异议；
2. **僵局早停（防空转）**：同一阻断项连续 **2 轮**修复仍未实质收敛，或触发偏差止损红线——提前中止，整理根因、两轮尝试与卡点交由用户决策（或改派高思考模型收尾）；
3. **达到上限**：已完成 **5 轮**独立复审仍未达成一致（强制停止，不得继续空转）。

### 外部评审返工条款

当用户将本轮成果交给外部模型或人工复审并带回修订意见要求返工时，落地修改（及代码变更后重跑受影响的联调/产物）后，**同样执行本闭环**（新拉 1 个独立审查节点如 `reviewer-v2`），重点核查：外部评审条目是否全部落地（含执行单与文档旧表述清理）、修复是否引入新回归、以及受影响的验收/联调是否基于最终代码重跑。

### 第 5 步：落盘记录、终检与向用户汇报

无论一致通过、僵局早停还是满 5 轮停下：

1. 若本次任务有执行单，将完整复审结果追加写入该执行单末尾；
2. **汇报前 3 项一致性终检（防止收尾引入低级失误）**：
   - 运行 `git diff --stat` 与 `git status`，核对与即将汇报的改动文件清单完全一致；
   - 核实收口策略已遵守（默认未提前勾选任务追踪项、未 `git commit` / `git push`）；
   - 逐项核对即将汇报的测试数、校验结果、验证方式（实操 vs 模拟）与最后一次实测命令输出逐字一致。
3. 在对话中向用户精简汇报：
   - **闭环结果**：共进行几轮复审、结束原因（一致通过 / 僵局早停 / 达到 5 轮上限）；
   - **每轮问题与处置**：阻断项如何修复、非阻断建议采纳或留档情况；
   - **未决分歧或僵局卡点（如有）**：并列呈现审查方观点、实施方证据/尝试，交由用户裁决；
   - **验收证据**：测试、lint/类型检查、只读校验、联调等实测命令与精确结果；
   - **待审改动文件清单**：方便用户审阅或转交外部模型复审，并明确标注当前尚未 commit。
