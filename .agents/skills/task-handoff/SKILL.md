# Task Handoff Drafting, Revision & Freeze

收到“推进下一步”、起草某个任务执行单、根据用户/外部模型审稿意见修改执行单，或在用户拍板后定稿锁版时，按本规范执行。

**核心目标**：由高思考模型一次性把摸底、技术决策、接口契约与坑点彻底想透，产出一份**脱离当前对话也能让较轻/便宜模型零歧义照图施工**的“单源真相（Single Source of Truth）”执行单。本规范不绑定特定 CLI、模型或技术栈，支持自动降级。

## 第 0 步：项目上下文发现（零配置可用，有约定优先继承）

执行任何操作前，先只读检查目标仓库根目录的规范文件（若存在，如 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 或项目约定的规则文档），提取并继承以下项目配置（未约定项使用默认值）：

- **项目红线**：禁止读取或修改的目录/文件、禁止运行的副作用命令、只读基线保护等；
- **执行单路径**：默认 `docs/handoffs/<task>-handoff.md`（若项目另有约定则从其约定）；
- **任务追踪源**：如 `specs/*/tasks.md`、`TODO.md`、Roadmap、Issue 列表等（若无，则以用户当前描述为准）；
- **验收门禁与附加产出**：项目约定的测试/lint/类型检查/构建命令、需要同步更新的文档或变更日志；
- **首选模型配置**：若项目指定了高思考设计模型名，优先采用。

## 绝对红线

- **严格遵守项目红线**：完整继承第 0 步发现的所有项目禁止事项（禁读目录、只读基线保护等）。
- **设计阶段只写执行单**：仅创建或更新目标执行单文件（默认 `docs/handoffs/<task>-handoff.md`），**不得改动业务代码、测试、配置或历史产物**。
- **未经用户明确同意不得开工**：汇报执行单及待拍板决策后立即停步，等待用户拍板并完成定稿后再进入实现。
- **不做内部二次审稿**：写完执行单直接汇报给用户，由用户决定直接拍板、发外部模型复审或另开终端复审。

## 派发与生命周期（高思考设计 + 跨 CLI 降级）

1. **首选 · 单节点高思考设计师（适用于支持按模型/思考等级拉起单节点的工具，如 Antigravity 的 `swarm`）**：
   - 若当前主会话运行在较轻/经济档位，拉起**且仅拉起 1 个**设计节点：
     - `name="designer"`、`workspace="inherit"`（不建 worktree，严禁并发拉起多个节点）；
     - 指定当前可用列表中的高思考/强推理档位模型：优先采用项目指定的设计模型；未指定时，**默认选同系列 `High` 档位（如 `*-high`）**（仅在 `High` 不可用时就近回退，**不默认自动升级到 `XHigh`**，除非用户或项目规范明确要求）。
   - **给 `designer` 的 `brief` 必须明文包含以下 4 项**（新节点看不到主会话上下文，不得省略）：
     1. **本 skill 的实际文件路径**（由主会话填入当前加载到的 `task-handoff/SKILL.md` 真实路径，切勿写死 `.agents/skills/...`），要求先完整阅读该文件（及同目录 `references/handoff-template.md`）并严格执行；
     2. **本次目标范围**（如“评估下一步推荐任务并起草执行单”、“围绕需求 X 起草执行单”或“按以下审稿意见修订 `<handoff_path>`”）；
     3. **红线重申**：只读摸底，仅允许创建或修改目标执行单文件，严禁修改任何其他文件，并列出从项目规范继承的全部红线；
     4. **汇报要求**：完成后汇报执行单路径、推荐理由（或修订摘要）与待拍板决策清单。
   - **保留上下文以承接修改（关键）**：初稿完成后**不要 `kill` `designer`**，让其进入 `waiting` 休眠状态（不消耗额度且完整保留摸底上下文）。
   - **后续审稿修改**：若同一会话内用户贴回自己或外部模型的审稿意见要求修改，主会话**直接转发给休眠中的 `@designer`**，由它核实意见、原地修订执行单（同步清理旧表述残影）并逐条回应；若处于新会话、原 `designer` 不存在，则读取已落盘执行单与审稿意见后新拉 1 个 `designer` 修订。
   - **拍板定稿（Freeze）与回收时机（关键）**：
     - 当用户明确拍板同意实施时，**先定稿再回收**，确保交到实施方手上的文档无条件分支、无歧义：
       - 若用户选了非推荐项、提出了微调，或执行单正文中存在“若选选项 B 则…”等条件分支：通知休眠中的 `@designer` 原地定稿——将拍板决议写入文档顶部（`状态：已拍板定稿（待实施）`），把被淘汰选项的分支文案从正文中折叠清除，并全文检查消除前后矛盾；
       - 若用户全按默认推荐项拍板且正文已无条件分支：由 `@designer`（或主会话直接）在文档顶部写明 `状态：已拍板定稿（待实施）` 与拍板决议摘要即可。
     - 定稿落盘后（或用户明确取消该执行单时），**立刻回收（`kill`）`designer` 节点**，并用 `git status` 确认未误改其他文件，随后由主会话（较轻/便宜模型）严格按定稿执行单施工。
2. **降级 · 当前会话直接起草**：
   - 若当前主会话本身已是高思考/强推理模型，或当前 CLI 不支持单节点精确指定模型，则直接在当前会话按下方规范完成摸底、起草、修订与拍板定稿。

## 起草前只读摸底清单（严禁凭记忆编造）

起草执行单前，必须先做只读核实：

1. **规范与任务源**：核对项目规范文件、任务追踪清单（若有，如 `tasks.md` / `spec.md` / Roadmap / Issues）的依赖关系、前置条件与未完成项；若用户直接给出了明确需求，则核实需求边界与项目既有约束；
2. **上下文承接**：核对相关上游执行单（已存在的目标任务备忘、最近完成任务的遗留待办或已知限制）；
3. **代码与测试现状**：核对涉及源码的真实符号与行号（`file:line`）、既有调用方与相关测试（特别注意既有测试的 mock / stub / monkeypatch 约束）、以及相关配置/数据/产物基线；
4. **环境与第三方依赖实测（防版本踩坑）**：凡任务涉及第三方库关键 API、框架生命周期、并发/IO 行为或未曾调用过的系统接口，**必须用只读命令或直接阅读已安装库源码实测本机实际版本与行为**，严禁凭训练记忆写 API 用法。

## 执行单必备结构（人机分层，高信噪比）

为便于用户快速拍板、同时让实施方零歧义施工，执行单须遵循**人机分层**与**单一事实源（去重）**原则——同一红线、口径或参数只在一个归属章节写死，避免多处重复导致修订时遗留前后矛盾。

标准 Markdown 骨架见 [references/handoff-template.md](./references/handoff-template.md)。

> **按任务类型裁剪**：对代码/工程任务，以下各节均须写透；对纯文档/演示剧本/验证记录类任务，第 6 节“接口契约”可改为“文档结构与事实口径契约”，但仍须保留范围清单、原子步骤、确定性核查项与止损规则。

### 上篇：面向用户决策（精简）

1. **顶部元信息与红线声明**：
   - 标注 `状态：待用户审阅拍板`（定稿后改为 `已拍板定稿（待实施）`），写明 Git 基线（分支/commit）及关键依赖基线；
   - 精炼列出本项目不可逾越的红线（继承自项目规范 + 默认收口策略：未确认前不 `git commit` / 不勾选任务清单）。
2. **任务目标与选择理由**：
   - 明确本次任务编号/名称与目标；若从多个候选任务中挑选，横向对比其他未完成候选项，说明为何优先做它（以及为何合并或不合并相邻任务）。
3. **待用户拍板的决策清单**：
   - 仅列出真正需要人拍板的取舍（范围粒度、交互/方案取舍、风险/兼容性权衡等），编号列出选项、明确推荐项与理由，便于用户直接回复如 `1A 2A 3A` 或转交外部模型审稿；
   - **定稿后折叠**：拍板后将结论固化进正文并清理落选分支描述，不把分支判断留给实施方。

### 下篇：面向实施方（较轻/便宜模型）的零歧义施工图

4. **现状锚点与环境陷阱预警**：
   - 给出本任务依赖或复用的现有关键代码锚点（精确到 `path:line` 与职责）；
   - 单列只读实测确认的**环境/第三方库版本陷阱与底层隐患**（写清“踩坑表现 → 必须采用的写法”），防止实施方踩坑空转。
5. **改动范围表与明确不做清单（Non-Goals）**：
   - **文件改动表**：逐行列出每个文件的 `路径 | 操作（新增/修改/微调） | 精确职责`；
   - **明确不做清单**：显式点名邻近但本次**严禁修改**的模块、配置、只读产物与下游任务，防止实施方“顺手重构”越界。
6. **精确接口与行为契约（施工核心，不留猜想空间）**：
   - 对每个新增或修改的函数、类、数据结构、API 端点或 CLI 子命令，给出：
     - **精确签名**：文件路径、名称、参数名、类型、默认值、返回值；
     - **复用约束**：明确指定必须复用哪个现有符号（带 `file:line`），禁止重复造轮子；
     - **边界、异常与退出码口径**：空输入、空值、非法值、缺失资源、外部服务异常、只读保护等分别应抛何种异常或返回何种错误码/退出码，明确禁止静默吞错或静默降级创建脏状态；
     - **兼容性约束**：点明被改符号的现有调用方与既有测试（含 mock/stub 替身）必须保持兼容的具体写法。
7. **原子化施工步骤（自底向上，每步可自检）**：
   - 按依赖从底层到上层编号（`Step 1 → Step N`）；
   - **每一步写明**：改动哪几个文件 + 具体改动点 + **本步完成后立刻可跑的最小验证命令**，让实施方小步闭环，不攒到最后才发现崩溃。
8. **确定性测试矩阵与验收门禁**：
   - 严禁把非确定性判断（如依赖外部在线 LLM 自由发挥、未固定时钟/随机种子）写进单元测试；
   - 给出**测试矩阵**：逐条写明目标测试文件路径、测试场景（覆盖 **正例 + 关键边界 + 异常反例 + 既有兼容回归**），并**写死关键断言底线**（例如必须断言具体返回值/透传参数/精确错误类型与退出码/状态落盘与回滚，明确禁止仅断言非空或退出码为 0 等弱断言）；
   - 给出可直接复制执行的完整门禁命令清单（项目约定的单元测试、全量测试、lint/类型检查、构建/只读基线校验、`git status`，以及需要人工/实机联调时的独立验收步骤）。
9. **项目附加产出要求（按需）**：
   - 若项目规范要求同步更新特定文档（如架构文档、变更日志、学习笔记、API 文档、README 等），明确精确目标文件与更新要点；若无则省略本节。
10. **实施方偏差止损规则（固定模板，写入执行单末尾）**：
    - **可自决微调**：内部私有变量名、局部辅助函数拆分、注释与格式调整（不改变对外契约与测试预期）；
    - **必须立即停工上报（严禁擅自绕过）**：发现既定签名/契约与仓库现状冲突、需要修改清单外文件、需要改写既有测试的预期断言、需要放宽安全/只读/隔离红线，或实测发现新的第三方库/环境阻断问题。

## 汇报给用户的格式

起草、修订或定稿完成后，在对话中精简汇报：

1. **执行单链接**（clickable `file://` 路径）；
2. **核心说明**：
   - 初稿：说明**任务目标/为什么优先做它**及摸底发现的最关键技术风险与锚点；
   - 修订：说明本轮按审稿意见修改了哪些要点，以及对有异议条目的核实证据；
   - 定稿：确认已将拍板决议折叠进正文、无前后矛盾、已回收 `designer`（若曾拉起）并核验 `git status` 干净；
3. **待用户拍板的决策清单**（初稿/修订阶段编号列出，便于直接回复如 `1A 2A` 或转交外部模型审稿）；
4. 初稿/修订阶段明确说明**尚未改动任何代码，等待确认后再定稿开工**。
